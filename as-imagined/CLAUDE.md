# As Imagined — Project Guide for Claude Code

## What this project is

**"As Imagined"** is a solo-developed Pokémon project in Godot 4.7/GDScript
(migrated from 4.3), set in **Kanto** with an **original story**. It ships
**two co-equal sister products from one shared engine**:

1. a **full single-player Pokémon RPG**, and
2. a **standalone Showdown-style battle simulator** with team builder.

**The battle engine is the shared foundation both sit on — a subsystem, not
the product itself.** Neither product is "the real one"; the simulator is not
a stepping stone to the RPG, and the RPG is not a wrapper bolted onto the
simulator. Work that improves the shared engine serves both.

The farming/action-RPG hybrid project is a **completely separate, unrelated
project**. Do not assume any code, autoloads, or conventions from that project
carry over here unless Rob explicitly says so. (This supersedes an earlier,
long-standing "flagged, not resolved" note in this file that left open whether
the two were the same project described twice — they are not. That question is
closed.)

## Ground truth / reference

**`pokeemerald-expansion` is the primary, first-stop reference — for mechanics,
overworld/map behavior, UI, and art alike.** It is the default starting point,
not a mandate.

### The procedure

1. **Scope the relevant `pokeemerald-expansion` behavior/assets first.**
2. **Then confirm direction with Rob before proceeding.**
3. **Where `pokeemerald-expansion` doesn't cover something**, research the
   option space — other reference sources, plugins/addons, custom
   implementation — and **bring Rob choices with a recommendation.**

Two failure modes this procedure exists to prevent, both explicitly
disallowed:

- **Never substitute a source or improvise unprompted.** If the reference
  doesn't cover it, that is a decision point for Rob, not a licence to pick
  something yourself.
- **Never simply stop at "not covered."** "The reference doesn't have this"
  is the beginning of the research task, not the end of it.

The reference is also **not** the Bulbapedia prose description and **not**
vanilla `pret/pokeemerald` — vanilla Emerald is missing the mechanics this
project wants (Physical/Special split, newer movepool, newer abilities), so
it's not the right reference here. This project targets
`pokeemerald_expansion`'s **expanded/upgraded battle engine** (DizzyEgg's
battle engine upgrade, RH-Hideout community). Modern conveniences and
later-gen mechanics are in scope and expected — not just what shipped in the
original 2004 release.

### Key files to consult when implementing a mechanic

- `src/battle_script_commands.c` — move/effect execution logic
- `src/battle_util.c` — damage calc helpers, status application
- `src/battle_ai_script_commands.c` and `src/battle_ai_main.c` — trainer AI
- `src/data/moves_info.h` / similar — move data tables
- `src/data/abilities.h` — ability definitions
- `include/constants/battle_move_effects.h` — move effect IDs

When implementing any mechanic, the workflow is: **look at the source logic
first, then port the behavior to GDScript** — don't guess from memory of "how
Pokémon battles work," since even the expanded engine has specific numeric
constants and edge cases worth confirming against source rather than assuming.

If a mechanic's source location is unclear, search the repo structure before
implementing, or ask Rob to confirm before making something up.

## Tech stack

- **Engine:** Godot **4.7.x**, Standard edition (GDScript, not C#/.NET) —
  confirmed directly via `project.godot`'s own `config/features=PackedStringArray
  ("4.7", "Forward Plus")` field (2026-07-18), not assumed from memory. The
  project was migrated from 4.3; see "Standing infrastructure note: Godot
  engine version" below for the full 4.3→4.7.1 migration history and the
  status of the old binary. If you ever see "4.3" cited as current for this
  project (in an older or external handoff doc), treat it as stale.
- **Why GDScript:** consistency with Rob's other Godot project (the
  farming/action-RPG hybrid — a completely separate, unrelated project, see
  "What this project is"), plus standard edition keeps Web export available
  if ever wanted.
- **Data format: TWO LAYERS, deliberately — corrected 2026-08-07.** The old
  wording here said `.tres`, one file per entry, *"don't mix formats"*, and
  cited `[M1] Data format`. **Every clause of that had become false**, and a
  session reading it would either "fix" a working design or conclude the
  project had drifted. What the codebase actually does, measured:

  | | JSON | `.tres` |
  |---|---|---|
  | Holds | the **full reference dataset** | the **implemented subset** |
  | Read by | `PokemonRegistry` — bulk lookups, names, dex data, learnsets | the **battle engine** — loaded by id as live typed objects |
  | Shape | parsed once at boot into dictionaries | `load("res://data/moves/move_%04d.tres")` on demand |

  **The counts are the proof, not the suggestion.** `moves.json` holds 935
  entries and `data/moves/` holds **717** `.tres` — which is exactly M19's
  *"717 implemented, 217 excluded"* (717 + 217 + 1 = 935). Items are the same
  shape: all 816 in `items.json`, only the ones with real held-item behaviour
  as `.tres`. ⚠️ **This is why `ScriptVM._resolve_trade_held_item` tests
  `ResourceLoader.exists(".../item_%04d.tres")` before loading — that check is
  not defensive, it is asking "do we implement this item?", and the file's
  existence IS the answer.** Consolidating the two formats would destroy that
  property.

  `gen_moves.py` emits both from one source in one run, so the two views
  cannot drift.

  ⚠️ **SPECIES ARE JSON-ONLY. There is no `data/pokemon/` directory.**
  `PokemonSpecies` resources are BUILT AT RUNTIME from `pokemon.json` by
  `PokemonFactory.build_species()`, which also normalises real data quirks on
  the way through (mono-typed species are stored as the same type twice, e.g.
  Pikachu `[14, 14]`, not `[type, TYPE_NONE]`). Anything hand-editing species
  edits the JSON, not a resource.

  **The rule, restated:** full dataset in JSON, implemented behaviour in
  `.tres`, one generator emitting both where both exist. Adding a `.tres` for
  something the engine does not implement is the mistake to avoid — not the
  mixing.

  ⚠️ **`data/pokemon.json` IS HAND-OWNED — Rob, 2026-08-07: "the battle
  calculations and rhythm are to be source-exact as possible, but I control
  Pokémon stats."** Species base stats, types and abilities are AUTHORED.
  Battle mechanics stay source-exact; the creatures those mechanics operate on
  are Rob's to balance. Moving the file to `.tres` was considered and declined
  — one greppable, bulk-editable file with a one-line diff per stat beats 386
  inspector visits for the edits actually made.

  ⚠️ **THREE GENERATORS WRITE THIS FILE AND ALL THREE MUST KEEP MERGING** —
  `gen_weight_data.py`, `gen_exp_ev_yield_data.py`, `gen_species_names.py`
  each load the existing JSON, set only their own fields, and write back.
  **NEVER write a generator that rebuilds `pokemon.json` from the reference.**
  It is the obvious shape and it would silently erase authored balance across
  386 entries, with no error and no diff anyone would spot. No such path exists
  today; nothing but this note prevents one. Same exposure
  `docs/field_script_authoring.md` already guards for dialogue — see
  `docs/decisions.md`, `[M1-rev] data/pokemon.json is HAND-OWNED`.
- **External plugins/addons: research, recommend, Rob decides — not a blanket
  ban.** `pokeemerald_expansion` is where implementation *starts*, not a
  ceiling. When something doesn't exist there, or exists but doesn't translate
  to Godot, the process is the same as the reference procedure above: research

## Architecture overview

This tree is the **shape of the codebase**, not the whole design. The battle
simulator subsystem came first (M1–M26) and the overworld/RPG layer was built
on top of it starting at M27 — both are live, and neither is a wrapper around
the other (see "What this project is").

```
scripts/
  data/           # Data resource classes (PokemonSpecies, MoveData, AbilityData, ItemData)
  battle/
    core/         # BattleState machine, BattlePokemon (runtime instance), turn order/priority resolver, damage calculator
    moves/        # Move effect implementations, tiered by complexity
    abilities/    # Ability hook implementations
    ai/           # Trainer AI decision logic
  overworld/      # Step resolver, MapManager/chunks, entities, ScriptVM, bag/wallet/flags, save
  ui/             # Battle HUD, menus, text box controller
scenes/
  battle/         # Battle scene(s), UI scene(s), battle verification suites
  overworld/      # overworld.tscn (the generic controller) + overworld verification suites
  maps/           # Baked per-map artifacts — <Map>.tscn + <Map>_data.tres, hand-editable
data/
  moves/          # Per-move .tres (the implemented subset — see Tech stack)
  abilities/      # Per-ability .tres
  items/          # Per-item .tres
  *.json          # The full reference datasets (pokemon.json, moves.json, items.json, map_scripts.json, …)
field_script_source/      # Hand-authorable fork of the reference's field scripts + dialogue (project root)
reference/
  pokeemerald_expansion/  # Cloned source, read-only reference — never edit
docs/             # Design notes, scope docs, decisions log, build-log archives under docs/status/
```

⚠️ **There is no `data/pokemon/` directory** — species are JSON-only and built
at runtime by `PokemonFactory.build_species()`. See the Tech stack section's
own two-layer data rule, which is the authority on which format holds what.


### Core battle flow (state machine)

```
BATTLE_START
  → MOVE_SELECTION (both sides choose action: move / switch / item / run)
  → PRIORITY_RESOLUTION (determine action order: priority bracket > speed > random tiebreak)
  → ACTION_EXECUTION (loop per resolved action)
      → PRE_MOVE_CHECKS (sleep/freeze/paralysis/confusion checks, flinch)
      → MOVE_EXECUTION (accuracy check → effect application → damage calc → secondary effects)
      → FAINT_CHECK
  → END_OF_TURN (weather damage, status damage (burn/poison), held item effects, etc.)
  → FAINT_CHECK / SWITCH_PROMPT
  → BATTLE_END_CHECK (loop back to MOVE_SELECTION or end battle)
```

This skeleton should be built and tested with simple placeholder moves
(struggle-only or single tackle-like move) BEFORE any real move data is added.
Get the loop solid first.

## Working style / instructions for Claude Code

- Work one milestone at a time. Do not implement Tier 3 moves while Tier 1
  is still unverified.
- When implementing a move or ability, state which source file and function
  you're basing the behavior on.
- When a mechanic seems ambiguous or you're not fully certain of the engine's
  specific behavior, stop and ask rather than guessing — call out the
  ambiguity explicitly.
- Write unit-test-style verification scenes/scripts for damage calc and status
  logic as they're built (e.g. a debug scene that runs known move/stat
  combinations and prints expected vs. actual damage), since correctness here
  is foundational to the shared battle engine both products sit on. [The
  original wording was "the entire point of the project"; that was corrected
  once the battle engine was reframed as a subsystem rather than the whole
  product, and is corrected again here to reflect that it underpins *both*
  the RPG and the simulator. Correctness within it remains just as important.]
- Keep `docs/decisions.md` updated with any mechanic verified against source,
  especially when a constant or rule was ambiguous and required a judgment
  call — so we don't re-litigate it later.
- The scope is "what the expanded engine does," not "whatever I think would
  be cool." If you have an idea for a mechanic or balance change beyond what
  `pokeemerald_expansion` implements, flag it as an idea in `docs/` rather
  than just adding it.

## Standing rule: Step 0 — scope the real reference behavior before deciding anything

**"Step 0" is the name this project gives to its single most-used discipline.**
It was invoked 94 times across this file's own history before ever being
defined; this section is that definition, and every other rule that says "the
same Step 0 discipline" points back here.

**The rule: before deciding how to implement something — before choosing an
approach, an architecture, a data shape, or an asset — go and scope what the
real reference actually does.** Investigation comes first, direction second,
implementation third. Not the other way around.

This applies to all of it, not just battle mechanics:

- **Mechanics** — read the actual source function before porting it.
- **Overworld / map behavior** — read the real structures and dispatch order.
- **UI** — read the real window templates, layouts and proportions.
- **Art and assets** — identify and pull the real reference assets first (see
  the dedicated asset rule below, which is Step 0 applied to art).

**Why it is a named rule and not just good advice:** essentially every
expensive mistake recorded in this file traces to skipping it — building a
generic version first and retrofitting authenticity later, assuming a pair of
things behave symmetrically without checking, trusting a prompt-supplied
constant, or trusting a recon document's summary over the source it summarizes.
The recurring pattern is always the same shape: the work *looked* correct
because it was internally consistent, and the divergence from real behavior
only surfaced later, at higher cost.

**Step 0 findings are reportable output, not private scratch work.** When Step
0 turns up something that contradicts the task's own framing — a wrong ID, a
mechanism that isn't shared after all, an assumption that doesn't hold —
**say so explicitly before implementing**, rather than silently correcting
course. Several of this project's most valuable recorded corrections exist
only because a session surfaced its Step 0 finding instead of quietly
absorbing it.

**Step 0 does not end at "the reference doesn't cover this."** See the
reference procedure above: that outcome is the start of a research task and a
decision point for Rob, never a stopping point and never a licence to
improvise.

### Standing Step 0 checklist item: does this foe-targeting move's real script call `typecalc`?

Discovered independently four times before being made a standing checklist item: `[D2 batch 2]` (Foresight/Odor Sleuth), `[D4 bundle 3]` (Purify/Nightmare/Spite), `[D4 Bundle 6]` (Toxic Thread/Venom Drench), and the `[EFFECT_STAT_CHANGE audit]` that finally swept the rest of the family (16 more moves — Growl/Leer/Screech/etc.).

This project's `BattleManager._phase_move_execution` runs every foe-targeting move with a real type through one general type-immunity gate before letting the move's own effect logic run, on the assumption that real source similarly checks `typecalc` for every such move. That assumption is false for an entire family of status moves: any move whose real battle script never calls `typecalc` (confirmed so far: `BattleScript_EffectForesight`, `BattleScript_EffectStatChange` and everything that maps to it, `BattleScript_EffectReflectType`) is NEVER subject to a type-immunity check in the real engine — including against its own primary, flavor-intended use case (Nightmare vs. a sleeping Normal-type target; Toxic Thread vs. a Steel-type switch-in; a plain Normal-type stat-lowering move vs. a Ghost-type).

**Before implementing or auditing any foe-targeting status move (or move family) going forward**: read the move's real battle script directly (`data/battle_scripts_1.s`, or trace `sMoveEffectTable`/`battle_move_effects.h` to find which script the move's `.effect` maps to) and confirm whether it calls `typecalc` anywhere. If it does not, the move needs the same treatment as the precedents above — either its own dedicated `is_*` exemption (if it also needs its own dispatch branch for other reasons) or, if it's one of a family sharing a no-`typecalc` script, the shared `MoveData.stat_change_bypasses_type_gate`-style flag — checked against this project's own `TypeChart.TABLE` to confirm the exemption is actually reachable (not moot, like the 9 Memento-shaped exclusions above) before spending test-writing effort on it.

### Standing Step 0 checklist item: a new consumer of a dormant `MoveData` field needs a full-roster grep, not just the moves already in mind

A recurring gap shape across this whole M19/M21.5 arc: a `MoveData` field already exists in the schema and already has real ability/item logic reading it, but was never actually SET on every move that should carry it per source — only on the specific moves a session happened to be thinking about at the time. Confirmed instances: Ice Ball's `ballistic_move` (flagged in a comment since `[M16b]` but never actually set on the data dict until `[M17n-1]`), Air Balloon/Iron Ball's groundedness (`[M18t]`), Mega Punch/Headlong Rush's `punching_move` and Aerial Ace's `slicing_move` (M21.5 Session 3's Part 4 Punch-family check), and 69 more moves across 10 flag categories found by M21.5's own Bucket 1 full-roster sweep.

**Before building any new ability/item mechanic that reads an existing-but-previously-unconsumed `MoveData` field**: grep the full roster (`gen_moves.py`, or the reference `moves_info.h` struct field directly) for every move that should carry the flag per source — not just the specific named moves already in mind for that session. A session scoped to "does move X need this flag" will reliably miss sibling moves Y and Z that need the identical flag for the identical reason.

## Standing rule: port the behaviour, not the mechanism — "would a player notice?"

**Rob's call, 2026-08-07.** Fidelity to `pokeemerald-expansion` is about what the
game DOES, not how the engine does it. Where the two can be separated, this
project prefers whatever Godot does best.

**The test, and it is deliberately a blunt one:**

> **Would a player notice? If yes, match source. If it is only visible in a
> stack trace, use the engine.**

⚠️ **THIS IS NOT A LOOSENING OF STEP 0, AND IT IS NOT A LICENCE TO IMPROVISE.**
You still go and read the real function first — every time, and for the same
reasons. What changes is only what you do with what you find: having established
what the behaviour IS, you are free to express it the way Godot expresses things,
rather than transliterating C into GDScript.

⚠️ **IT IS ALSO NOT A CHANGE OF SCOPE.** "The scope is what the expanded engine
does, not whatever I think would be cool" still stands, unamended. This rule
governs IMPLEMENTATION, never the feature list. A mechanic the reference does not
have is still an idea to flag, not a thing to add.

### What is behaviour (match it)

Anything a player can observe, and anything a player's SAVE depends on:

- **Battle mechanics** — damage, accuracy, AI scoring, effect ordering, turn
  order, status rules. This is the product; both products sit on it.
- **Pulled assets** — sprites, fonts, window art, backgrounds. Real reference
  art, per the asset rule.
- **Script semantics** — the command vocabulary (17,137 imported labels depend on
  it), flag/var conventions, `applymovement` being asynchronous while
  `waitmovement` blocks, `trainerbattle`'s outcome routing, the interaction
  dispatch order including the counter hop.
- **Text** — control codes, page splits, and how many times the player presses A
  to get through a conversation.

### What is mechanism (use Godot)

Anything only a developer sees:

- Data structures, file formats, class layout, how state is stored.
- Scheduling — how a thing is made to happen over several frames.
- Input plumbing, draw-order plumbing, resource loading.
- Anything whose GBA shape exists because of a hardware constraint this project
  does not have.

### Worked examples, both directions

**Diverged, correctly.** `ScriptVM` is a Godot-native interpreter over a JSON IR,
not a byte-level VM over a 231-entry command table. No ROM is ever loaded, the
importer reads assembly TEXT, and the JSON is greppable and hand-editable —
which is what made `field_script_source/` possible at all. A player cannot tell.

**Diverged, correctly.** `native` (M27G G5) lets a script hand control to
arbitrary Godot code. It is a port of source's own `SetupNativeScript`, but the
handler is a Callable in a registry rather than a function pointer in a table —
and handlers may be coroutines, which source has no concept of.

**MATCHED, correctly, and it looked like plumbing.** `applymovement` queues and
returns while `waitmovement` blocks. Collapsing that into one blocking call is
the obvious "simplification" and would break every cutscene where two actors
move at once — which is most of them. ⚠️ **Async/sync IS behaviour**, however
much it reads like implementation.

**MATCHED, correctly, after nearly not being.** `trainerbattle`'s three outcomes
resolve to two DIFFERENT continuation points, and the already-beaten skip lives
one level below the command. A tidier design would re-challenge Brock forever.

### The failure mode this rule exists to prevent — in BOTH directions

- **Porting plumbing you did not need.** A GBA task scheduler reimplemented in
  GDScript so that ported scripts have something to run on, when
  `AnimationPlayer` already is one.
- **"Simplifying" something load-bearing.** The two matched examples above both
  look like implementation detail from the outside and are not.

**When genuinely unsure, the tiebreak is Step 0 plus this file's own reference
procedure: scope it, then bring Rob the call.** Guessing in either direction is
the thing to avoid — and a divergence, once chosen, is recorded at the site like
every other one here.

## Standing rule: flag, don't silently fix, out-of-scope findings

**When work turns up a real problem outside the current task's scope, flag it
— do not silently fix it.** Record it (in this file, in `docs/decisions.md`,
or in the session's own report, as appropriate), state plainly that it was
found and deliberately not fixed, and let Rob decide when it gets picked up.

This is a long-standing discipline in this project, previously recorded only
as an aside inside a review section that has since been retired. It is stated
here as a standing rule in its own right because it is what makes the
project's flagged-item trail trustworthy: a finding that was quietly fixed
mid-task leaves no record, no test, and no decision, and the next session
cannot tell the difference between "this was considered and handled" and
"this was never noticed."

The complement matters too: **a flagged item is not a dropped item.** Flagged
findings are expected to land somewhere real — a milestone, a sub-phase, or an
explicit deferral — rather than living indefinitely as prose.

## Standing rule: never trust the shell's working directory — absolute paths, always

**This one rule replaces what were previously three overlapping rules**
(`pwd`-before-Godot, absolute-path sweep dispatch, never-`cd`-into-the-
reference-tree). They were separate because each was written after a different
recurrence of the same underlying failure. They are one problem family, and
splitting them is part of why the failure kept recurring: a session would
recognize "this is a Godot invocation" but not recognize "this is a grep into
the reference tree" as the same rule.

### Two distinct root causes — both real, do not conflate them

**Cause 1 — the shell persists and never auto-resets.** `bash_tool` sessions
share ONE persistent shell across all tool calls — there is NO automatic reset
to the project root between calls. When a command `cd`s into
`reference/pokeemerald_expansion/` to read source, that `cd` persists into
every subsequent bash call for the rest of the session, not just the one
command it was meant for.

*Occurred 3× across sessions — `[M18.5d Phase 2]`, `[M18.5d-3]`, and one
earlier unlogged instance.*

**Cause 2 — the environment silently intercepts `cd` and lies about it.** The
true git repository root the tool environment enforces is
`/home/rob/GodotAsImagined` — **ONE LEVEL ABOVE** this project's own
directory, `/home/rob/GodotAsImagined/as-imagined`. Confirmed directly:
running `cd /tmp` (a path outside that repo) does not actually move the shell
to `/tmp` at all — the environment silently intercepts it and resets the
shell's cwd to `/home/rob/GodotAsImagined` (the repo root), not to
`as-imagined`, and not to wherever the `cd` target was.

Any command, at any point in a session, that causes a `cd` outside the git
repo boundary — **not just the reference-tree case in Cause 1** — silently
lands the shell one level too high, and every subsequent RELATIVE-path command
then fails with `No such file or directory`.

> **Cause 2 is the more dangerous of the two: a correctly-written `cd` can
> fail while appearing to succeed.** This is why the failure recurred across
> so many sessions despite each one being individually "fixed" — the true
> trigger is broader than "forgot to `cd` back from the reference tree," and
> no amount of care about that one specific case fully prevents it.

### The rule

1. **Always use the full absolute path, in the SAME command string.** Never a
   bare relative path, and never relying on a `cd` from a prior, separate
   command in the session.

2. **Never `cd` into `reference/pokeemerald_expansion/` for a one-off read.**
   Reference the full absolute path directly instead:
   ```
   grep -rn "..." /home/rob/GodotAsImagined/reference/pokeemerald_expansion/src/*.c
   ```
   — this works identically regardless of the shell's current directory and
   leaves no persistent state to drift.

3. **If a `cd` into the reference tree is genuinely needed** (e.g. a
   multi-step sequence of relative-path commands), chain the return in the
   SAME command:
   ```
   cd reference/pokeemerald_expansion && <commands> ; cd /home/rob/GodotAsImagined/as-imagined
   ```
   — never leave a reference-tree `cd` unpaired.

4. **Do not rely on a preceding `cd` in the same dispatch as the fix either**
   (e.g. `cd /path && bash scripts/count_assertions.sh ...`) — this has also
   been observed to fail in this environment, likely for the same class of
   reason (a `cd` cannot be trusted to land where requested). The
   absolute-path invocation needs no `cd` at all and is the one mechanism
   confirmed to work without a retry.

5. **`pwd` before every Godot invocation remains required** as a second line
   of defense, **not a replacement for rule 1** — if it ever shows anything
   other than `/home/rob/GodotAsImagined/as-imagined`, `cd` back explicitly
   before proceeding, do not assume the next command will self-correct.

   > A `pwd` check placed before a Godot call catches this AFTER it's already
   > happened; it does not prevent the drift, since the triggering `cd` may
   > have occurred several tool calls earlier in the session, not the one
   > immediately prior.

### Trigger contexts this rule covers — all of them, not just Godot

This is the enumeration that keeps getting lost. **Every one of these is the
same rule:**

- **Any Godot invocation** — single test runs, `--import` passes, and full
  sweeps alike
- **Full regression sweep dispatch**, foreground *or* background — do not
  special-case background dispatch as "probably fine this time"
- **Any read into the reference tree** — `grep`, `find`, `cat`, `sed`,
  anything
- **Any Python/data-pipeline script run** (`gen_moves.py`, `gen_items.py`,
  etc.)
- **Generally**: any workflow that assumes a `cd` to a path outside
  `/home/rob/GodotAsImagined` succeeded should be treated with suspicion;
  prefer absolute paths over `cd`-and-relative-path sequences wherever the
  destination might be outside the repo

**WRONG** (drift-prone — a separate/prior `cd` does not persist):


### Diagnosing a suspected instance

If a Godot command times out or produces no output, check the invocation for a
bare `--path .` or `--path as-imagined` **before assuming a real test hang.**
The symptom is a silent hang, not a clean error — Godot has no `project.godot`
to find and waits until the `timeout` wrapper kills it, often 1–4+ minutes
later.

> `scripts/count_assertions.sh` was already hardened this way after
> `[D4 CHEAP bundle]`'s own investigation found this exact pattern silently

> single-scene runs, which is where it keeps recurring.

## Testing conventions — the checklist

Every convention below was written after a real bug and names the milestone(s)
it cost. **Treat each as a known risk from the first draft of any new test, not
as something to catch reactively after a false pass slips through.** The full
reasoning, the worked example of the test that broke, and how it was fixed live
in **`docs/testing_conventions.md`** — read that when one of these bites, or
before writing a test in a shape it covers.

1. **Snapshot via signals, not post-battle state.** A test Pokémon whose only
   move is repeatable will re-cast it every turn after the action queue drains,
   so state read after `start_battle()` returns is not the state under test.
   *(M16c, M16d)*
2. **Lambda-captured scalars are snapshots, not references.** Wrap the value in
   a single-element `Array` and mutate index `0`. *(M16c, M16d, M16e, M17a)*
3. **Type immunity precedes ability logic.** A 0× matchup means the ability
   under test never runs and `0 == 0` passes. Check the pairing against
   `TypeChart` before writing the scenario. *(M17b, M17c)*
4. **Pairwise damage comparisons must force every RNG input** — both
   `_force_roll` AND `_force_crit`, on **every** scenario being compared.
   *(M17n-2, M17l)*
5. **`force_crit` bypasses crit-STAGE math.** It short-circuits to an outcome,
   so it cannot test Super Luck, Scope Lens, Focus Energy or stage composition.
   Call the stage function directly, or use a statistical sample. *(M17n-5,
   M18e)*
6. **Aggregating across an uncontrolled number of turns breaks absence checks
   AND rate measurements.** `start_battle_with_parties` runs the whole battle;
   isolate the event or pin the trial. *(M17l, M18k)*
7. **Check `current_hp > 0`, not `.fainted`, for synchronous aliveness.** The
   flag is set in a later FAINT_CHECK phase. This one is an implementation
   risk, not a test-methodology one. *(M18d, M18n)*
8. **`scenes/battle/integration_test.tscn` prints a third format** (`"Integration
   tests: N passed, M failed"`) — an ad-hoc recount that matches only the two
   common formats silently drops its 24 assertions. *(M17f, M17g, M17n-7)*
9. **A baseline total needs two independent methods, cross-checked, run twice.**
   `scripts/count_assertions.sh` alone is not sufficient evidence for this
   particular number, which has been wrong at least six times running.
10. **A meaningful sweep shortfall is a regression; a tiny one may be noise.**
    1–3 assertions short in a known-statistical suite is background noise;
    anything more is a regression. **Never adopt a lower total without
    root-causing it.**
11. **`"a" + "b %d" % [x]` binds `%` only to the trailing literal.**
    Parenthesise. *(M18.5d Phase 2)*
12. **A wide sweep must grep `passed|fail` case-insensitively**, not the literal
    `FAILED` — 5 suites never print that word, and 3 genuinely broken ones
    passed 4 consecutive sweeps because of it. *(M18.5h-1)*
13. **Stat sub-field enumeration is exactly 7 field names** (`attack`,
    `defense`, `spAtk`, `spDef`, `speed`, `accuracy`, `evasion`) and must be
    counted as distinct nonzero sub-fields per block, never as token
    occurrences. *(M19 secondary-stat audit)*

## Standing process rule: pull real reference-game assets/structure first, iterate from there

**For any new UI element, screen, or visual component, the default approach
is to identify and pull the real reference-game assets and structure (art,
fonts, layout proportions, styling/color conventions) FIRST — confirmed via
direct source inspection, the same Step 0 discipline already standing for
everything else in this project — and build against that real, source-
accurate baseline from the start.** Only iterate/adjust from there, rather
than building a generic/placeholder version first and retrofitting
authenticity in a later pass.

**Why this is a standing rule, not just advice**: M25h's own sequence is the
concrete cost this rule exists to prevent. The shared bottom region was
built generically in M25h-1 (real proportions, no real art at all); a
dedicated follow-up session (M25h-1.1) was then needed to discover and wire
the real `text_window` border art; a further recon session immediately
after that found the TEXT rendered inside that same border still isn't
using any real font/styling. Three separate sessions to reach one
authentic-looking element, each one re-discovering and re-verifying a layer
that could have been identified and sourced correctly the first time, had
the real baseline been pulled before anything was built.

**This does not preclude iteration or legitimate project-specific
deviations** made AFTER understanding the real baseline — e.g. M25h-1.4/
h-1.5's own decision to build real separate Bag/Party screens, or M25h's own
earlier menu-simplification calls. Those are informed design choices made
with the real source already in hand, not a license to skip investigating
it in the first place.

**Not retroactive.** This governs new UI work going forward; it does not
imply any already-completed session should have followed it, and no prior
session's own history is rewritten to suggest otherwise.

## Known limitation: `git stash` is blocked by this environment's permission classifier

Discovered during `[M23.4]`, attempting to capture a clean "before" sweep
baseline. `git stash` (including `-u`) is blocked outright by this
environment's own action-classifier layer — not a repo/permissions issue,
a tooling-level block.

**Workaround that DOES work, for the narrow case of isolating untracked/new
files only**: `mv` the new files out to a temp path, run the sweep, `mv`
them back. This is what `[M23.4]` used to diff a "before" (no new files)
against an "after" (new files present) sweep total. Only valid when every
affected path is untracked (`git status` shows `??`) — moving a file is a
plain filesystem operation, not a git command, so it isn't subject to the
same block.

**No verified workaround exists for stashing modifications to
already-tracked files** — that case wasn't attempted or solved here, and
shouldn't be assumed solved. Flagged as an open gap for whichever future
session first needs to isolate uncommitted edits to existing files (e.g.
for a clean before/after sweep comparison mid-edit) rather than only new
ones.

### Status key — the `C/T/A` column (added 2026-07-26)

Every roadmap/status table in this file uses one narrow `C/T/A` column in
place of the old single ✅/🔶/⬜ box, which collapsed three genuinely
distinct states into one and hid the case that matters most: **work that
exists in the codebase but has not been signed off by Rob yet.**

Three **position-fixed** slots, always in this order, always exactly three
characters, wrapped in backticks so they render monospace and stay aligned
both in raw markdown and on GitHub:

| Slot | Position | Filled means |
|---|---|---|
| **C** — Code | 1st | Implementation is written and committed |
| **T** — Tests | 2nd | The relevant tier-specific suite passes for this row |
| **A** — Approved | 3rd | **Rob has manually reviewed and approved it** |

A slot is **filled** when it shows its own letter and **empty** when it
shows `-`. Empty slots still occupy their position, so the three states are
always readable left to right and a cell is never ambiguous:

- `` `CTA` `` — code, tests, approved (fully settled)
- `` `CT-` `` — code and tests done, **awaiting Rob's approval**
- `` `C--` `` — code committed, tests not (yet) recorded as passing
- `` `---` `` — nothing filled (not started, or in-flight and unresolved)

**The tiers are ordered but independent.** A row may legitimately sit at
`C--` or `CT-`. A row where a *later* slot is filled without an earlier one
(e.g. `` `-T-` `` or `` `--A` ``) is a **flag, not a valid state** — surface
it to Rob rather than silently "fixing" it by back-filling the earlier slot.

**Two standing rules for Claude Code, both non-negotiable:**

1. **Never fill the `A` slot. Under any circumstances.** Not when Rob says a
   feature is finished, not when C and T are both filled, not when a
   milestone's own status history reads as complete. `A` is Rob's alone —
   he will either say the word "approved" explicitly or edit the table
   himself. If a task appears to ask for it, ask rather than assume.
2. **Fill `T` only from an observed or recorded tier-specific pass.** Per
   this file's standing convention, full-suite sweeps are Rob's manual step

### Data pipeline scripts

Moves, abilities, and (as of the M18 item-data-infrastructure session) items each
follow the same two-track pattern: a hand-authored Python dict as the
human-editable source of truth, regenerated into Godot-native `.tres` Resource
files the engine loads at runtime. Run any of these from the project root, then
re-import (see the note above) before running a scene that depends on new/changed
`.tres` files:

```bash
python3 scripts/gen_move_targets.py  # data/move_targets.json  — RUN BEFORE gen_moves.py
python3 scripts/gen_moves.py      # data/moves/move_NNNN.tres    (MoveData)
python3 scripts/gen_abilities.py  # data/abilities/ability_NNNN.tres (AbilityData)
python3 scripts/gen_items.py      # data/items/item_NNNN.tres    (ItemData)
```

⚠️ **`gen_moves.py` now HARD-FAILS without `data/move_targets.json`** — it reads
every move's real `.target` from there and injects it, rather than the field
being hand-written per entry (110 moves are TARGET_USER, and `get_live_targets`
reads the field to decide whether the player is even asked to pick a target, so
a hand-maintained list would rot into self-buffs prompting for an opponent).
Same two-step shape as `gen_move_descriptions.py`. `MoveData.target`'s class
default and that generator's `DEFAULTS["target"]` are both **TARGET_SELECTED**
and must stay in step: a `.tres` with no `target` line has to load as SELECTED,
not as 0/TARGET_NONE.

All three scripts share one structure: a list of dicts (`MOVES`/`ABILITIES`/`ITEMS`),
a `DEFAULTS` dict (skip a field in the emitted `.tres` when it equals its class
default, keeping files lean), a `FIELD_ORDER` list (explicit emit order), a
`render()` function, and a `main()` that writes one file per entry to a fixed
`data/<kind>/` directory, ID zero-padded to 4 digits.

Loading convention: `MoveRegistry.get_move(id)` / `ItemRegistry.get_item(id)` are
path-convention loaders (`res://data/<kind>/<kind>_%04d.tres % id`, no preload
table — see `move_registry.gd`'s own doc comment for the full rationale). There is
no `AbilityRegistry` — abilities are loaded ad hoc per call site (`load("res://data/abilities/ability_%04d.tres" % id) as AbilityData`)
because `AbilityManager`'s actual mechanic dispatch is 100% hardcoded ability-ID
constants and never reads `.tres` fields at battle runtime; the `.tres` layer there
is a metadata catalog (name/description/ai_rating/interaction flags), not a
mechanism input. **Items follow the `MoveRegistry` pattern** (`ItemRegistry`,
`scripts/battle/core/item_registry.gd`), since item mechanics are likewise
hardcoded in `ItemManager` (`HOLD_EFFECT_*` constants) but item data may need
by-ID lookup from future non-battle code (team-building, UI) the same way moves
do.

**Item scope note:** as of M18a, `gen_items.py`'s `ITEMS` dict only contains the
40 items M18a actually implemented — every future M18 sub-tier (M18b onward) must
add its items there and regenerate `.tres` files, matching the moves/abilities
convention, rather than wiring item data inline into `ItemManager` or a test file.
See `docs/decisions.md`'s item-data-infrastructure entry for the full rationale
and the M18a-era gap this closed.
