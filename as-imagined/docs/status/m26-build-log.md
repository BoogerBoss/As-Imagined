Sub-numbers run in intended build order within each block. <br><br> **━━ M26A — Foundation & framework ━━** (the two cross-cutting changes everything else is built on top of; both complete). **M26A1 — Base resolution change** (was M26a): switch the project's logical/base viewport from Godot's generic 1152×648 (16:9) default to **1024×768 (4:3)**, using `window/stretch/aspect="keep"` instead of `"expand"` so the whole canvas letterboxes/scales as one unit rather than stretching. Revised from an earlier 1200×800 (3:2, the true GBA hardware ratio) once the Emerald UI Pack investigation found that pack's entire screen set — Bag, Party, Summary, Pokédex, Trainer Card — is uniformly 512×384 (4:3), matching Essentials' own native canvas; 1024×768 is a clean 2× integer multiple of that, keeping pixel scaling crisp. Deliberately not the strict GBA ratio: since most of M26's actual screen art comes from a stylized reskin pack rather than a pixel-exact ROM decode, holding a hard line on canvas *shape* while being flexible on asset *source* would be inconsistent — matching the pack's own native canvas once avoids re-fitting every individual screen against a ratio its source art was never drawn for. The small subset of genuinely GBA-native assets (this project's own `bag_frame.png` decode, real in-battle sprites, health boxes) don't need the outer canvas itself to be 3:2 to stay correct — they're sized to their own real ratio within the bigger 4:3 canvas instead, the same "resize the panel, don't stretch the asset" approach used throughout. Sequenced first, not just listed first: every already-shipped screen's own positioning (health boxes, sprites, message box, every M25h menu) was measured against the old 16:9 canvas and needed to land on the real final canvas before anything else was built or re-verified. Sprite positions specifically needed real re-tuning, not just re-verification: sprites are placed via a fixed-pixel-size box anchored at a single fraction point (confirmed directly in `battle_screen.tscn`), so their rendered size doesn't change with the resolution, but 1152×648 → 1024×768 is a real shape change (narrower, taller) that makes fixed-size sprite boxes occupy a different proportion of the screen. **M26A2 — Log/debug-overlay merge** (was M26b; carried over and substantially expanded from the former M25h-2, moved up to immediately follow the resolution change per explicit instruction; full design locked 2026-07-20): retire M25c's standalone always-visible accumulating log entirely; build one shared, **category-tagged** entry data structure feeding a single F3-toggled debug-overlay view, replacing two independent listeners with one.
